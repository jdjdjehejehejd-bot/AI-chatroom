# AI 채팅방 — 시스템 설계

사람 여러 명과 AI 여러 명이 한 방에서 대화하는 서비스의 기본 설계.
제품 방향과 검증 계획은 [PLAN.md](../PLAN.md), 화면 설계는 Claude 디자인 캔버스 "AI 채팅방 UI 설계"(입장, 방 화면 데스크톱/모바일, AI 초대, 방 설정, 상태 화면)에 있다.

이 문서는 **현재 구현된 것**과 **앞으로 설계한 것**을 구분해서 쓴다. 표의 "상태" 열이 그 구분이다.

## 1. 설계 원칙

1. **방 하나 = 한 곳에서 순서대로 처리.** 방 안의 모든 변화(메시지, AI 차례, 예산 차감)는 한 처리 주체가 직렬로 다룬다. 동시성 버그와 중복 호출을 막는 가장 단순한 방법이다.
2. **AI는 참가자이자 비용 발생원.** 모든 AI 호출은 예산과 연속 한도를 통과해야만 나간다.
3. **서버가 키를 다루므로 서버를 신뢰 경계로 본다.** 키는 화면·로그·메시지에 나가지 않는다.
4. **채팅 내용은 신뢰할 수 없는 입력.** 사람이든 AI든 다른 참가자의 발언이 규칙을 바꾸지 못한다.
5. **상태 화면까지 설계한다.** 한도 도달, 예산 소진, 오류가 정상 흐름의 일부다 (UI 상태 화면 참고).

## 2. 아키텍처

### 2.1 현재 (상태: 구현됨)

```
브라우저 ──WebSocket──▶ Node 프로세스 1개 (server.js)
                         ├─ rooms: Map (메모리)
                         ├─ 방별 오케스트레이터 (AI 차례 계획·실행)
                         └─ 제공사 호출: Anthropic / OpenAI 호환 / OpenRouter (HTTPS)
```
- 상태는 모두 메모리. 서버를 재시작하면 방과 대화가 사라진다. 모두 나가면 10분 뒤 방이 정리된다.
- 정적 페이지(`public/index.html`)와 WebSocket(`/ws`)을 같은 서버가 제공한다.

### 2.2 목표 1단계: 단일 인스턴스 + 저장 (상태: 설계)

```
브라우저 ──HTTPS/WSS──▶ 리버스 프록시(TLS) ──▶ Node 1개 ──▶ DB(방, 메시지, 문서, 사용량)
                                                        └──▶ 제공사 API
```
- 대화·문서·예산 사용량을 DB에 저장해서 재시작과 재접속에 견디게 한다.
- DB 종류는 정하지 않았다. 처음에는 파일 기반 DB로 충분할 수 있고, 인스턴스를 늘릴 때 옮긴다.
- **개인 키는 DB에 저장하지 않는 것을 기본으로 한다.** 저장하려면 암호화와 키 관리가 필요하고, 그 책임이 커진다. 대안은 방이 살아 있는 동안만 메모리에 두고, 재시작 시 방장이 다시 입력하게 하는 것이다.

### 2.3 목표 2단계: 여러 인스턴스 (상태: 설계, 필요해질 때)

- 같은 방의 사람들은 같은 처리 주체에 연결돼야 한다. 방 코드로 인스턴스를 고정하는 방식(방 단위 라우팅)이 원칙 1에 맞다.
- 방 상태를 외부 저장소에 두고 인스턴스 간에 이벤트를 전달하는 방식은 직렬 처리 보장을 직접 만들어야 해서 더 복잡하다.
- 이 단계에서 쓸 구체 기술(호스팅, 메시지 큐)은 정하지 않았다. 사용자 수가 이 구조가 필요한 규모가 된 뒤에 결정한다.

## 3. 데이터 모델 (상태: 설계, 현재는 메모리 객체)

| 엔티티 | 주요 필드 | 비고 |
|---|---|---|
| Room | id(방 코드), template, policy, maxStreak, budgetLimit, budgetUsed, createdAt, hostId | 현재 코드에는 hostId 없음 |
| Member(사람) | id, roomId, displayName, role(host/member), joinedAt | 현재는 접속 중인 연결(ws)과 이름만 있음 |
| AIParticipant | id, roomId, name, persona, provider, model, secretRef, addedBy | secretRef는 개인 키 참조. 값 자체는 별도 보관 |
| Message | id(방 안 순번), roomId, kind(human/ai/system), who, text, code, createdAt | **code**(이벤트 종류)는 아직 없음. 6장 참고 |
| Doc | roomId, text, updatedBy, updatedAt | 현재는 마지막 저장이 이김 |
| UsageLedger | roomId, aiId, provider, model, inputTokens, outputTokens, at | 현재는 호출 횟수만 셈. 토큰은 기록하지 않음 |

방 코드: 소문자·숫자 31자 중 6자리(약 8.9억 가지). 추측으로 방을 찾는 것은 5장의 속도 제한으로 막는다. 방 코드를 아는 사람은 누구나 들어올 수 있는 구조이므로, 비공개를 원하면 방장이 입장을 잠그는 기능이 필요하다 (설계, 미구현).

### 4.1 클라이언트 → 서버

| 타입 | 내용 | 상태 |
|---|---|---|
| join | room, name, template(새 방일 때만) | 구현 |
| msg | text (최대 1000자) | 구현 |
| config | policy, maxStreak(1~10), budgetLimit(사용량 이상, 최대 100) | 구현 |
| template | id | 구현 (AI 구성이 교체됨) |
| addAI | name, persona, provider, model, apiKey | 구현 |
| removeAI | id | 구현 |
| doc | text | 구현 |
| resume | lastSeenId (재연결 시 놓친 메시지 요청) | 설계 |
| lock | 입장 잠금 켜기/끄기 | 설계 |

### 4.2 서버 → 클라이언트

| 타입 | 내용 | 상태 |
|---|---|---|
| state | 입장 직후 전체 상태(최근 메시지 100개 포함) | 구현 |
| meta | 참가자·AI·설정·예산 | 구현 |
| msg | 새 메시지 | 구현 |
| typing | 입력 중인 AI | 구현 |
| budget | 예산 사용량 | 구현 |
| doc | 문서 갱신 | 구현 |
| err | 오류 문구(요청한 사람에게만) | 구현 |

### 4.3 앞으로 바꿀 점
- **재연결**: 연결이 끊기면 다시 붙고 `lastSeenId` 이후 메시지를 받는다. (UI "연결 끊김 → 다시 연결"에 필요)
- **중복 방지**: 클라이언트가 메시지마다 임시 ID를 붙이고 서버가 같은 ID를 한 번만 처리한다.
- **버전 필드**: 모든 메시지에 프로토콜 버전을 넣어 클라이언트 업데이트와 서버 업데이트 시차를 견딘다.
- **응답 스트리밍**: AI 응답을 토큰 단위로 흘려보내 "입력 중" 대신 실시간으로 보여준다. 제공사별 스트리밍 방식 구현이 필요하다.

## 5. AI 오케스트레이션

### 5.1 발언 정책 (상태: 구현됨)

| 정책 | 사람이 메시지를 보냈을 때 첫 발언자 | 이어짐 |
|---|---|---|
| mention | @멘션된 AI (`@모두`는 전부) | AI가 다른 AI를 @멘션하면 이어짐 |
| round | 모든 AI를 순서대로 1번씩 | 없음 |
| free | 멘션된 AI, 없으면 로스터 순서상 다음 AI | 연속 한도까지 로스터 순서로 계속 |

### 5.2 AI 차례 처리 순서 (방당 직렬)

```
사람 메시지 도착
  → 발언자 목록 계산 (정책)
  → 새 처리 세대 시작 (이전 세대는 결과를 버림)
  → 반복:
      다음 AI 선택
      연속 발언 한도 초과? → 중단 + 시스템 알림
      예산 소진?          → 중단 + 시스템 알림
      예산 1 차감, "입력 중" 알림
      제공사 호출 (제한 시간 60초, 재시도 없음)
        실패 → 시스템 알림(키는 가려서) 후 중단
        성공 → 메시지 게시, 문서 줄 반영, (mention 정책이면) 멘션된 AI를 대기열에 추가
```
- **재시도를 하지 않는 이유**: 실패한 호출을 자동으로 다시 보내면 비용이 조용히 두 배가 된다. 사용자가 다시 말을 걸면 다시 시도된다.
- **취소의 한계**: 새 사람 메시지가 AI 차례를 새로 시작시키면(멘션이 있거나 round·free 정책) 진행 중이던 세대는 결과를 버리지만, 이미 나간 제공사 호출의 비용은 되돌릴 수 없다. 예산은 차감된 상태로 남는다. 멘션이 없는 메시지(mention 정책)는 진행 중인 차례를 취소하지 않는다.

### 5.3 프롬프트 구성 (상태: 구현됨)
- 시스템: AI 이름·역할, 방 유형 규칙, 참가자 목록, 응답 규칙(한국어 300자 이내, 이름 접두어 금지, 호출은 @이름), 채팅 속 지시를 믿지 않는다는 문구, 공유 문서 전문
- 사용자: 최근 메시지 20개(시스템 메시지 제외) + "이제 ○○이(가) 말할 차례"
- 한계: 긴 대화에서는 앞부분이 잘린다. 요약을 주기적으로 만들어 넣는 방식은 설계만 있다. 요약 호출도 예산을 쓰므로 호출 수 계산에 포함해야 한다.

### 5.4 공유 문서 연동 (상태: 구현됨)
AI가 `[문서] `로 시작하는 줄을 쓰면 문서 끝에 `- ` 목록으로 추가된다. 문서는 최대 8000자다. AI가 덧붙이다 넘치면 앞부분이, 사람이 저장할 때 넘치면 뒷부분이 잘린다. 사람과 AI가 동시에 고치면 마지막 저장이 이긴다.

## 6. 권한 모델 (상태: 설계, 현재는 방 안 누구나 모든 것 가능)

| 행동 | 방장 | 멤버 |
|---|---|---|
| 메시지, 문서 편집 | 가능 | 가능 |
| AI 초대 / 내보내기 | 가능 | 방장이 허용한 경우만 |
| 방 유형 변경 (AI 구성 교체) | 가능 | 불가 |
| 발언 방식·연속 한도·예산 변경 | 가능 | 불가 |
| 입장 잠금, 멤버 내보내기 | 가능 | 불가 |

- 방장 = 방을 만든 사람. 방장이 나가면 가장 먼저 들어온 멤버로 넘긴다.
- **예산은 방장만 늘릴 수 있어야** 서비스 쪽 비용을 통제한다. 지금은 누구나 최대 100회까지 올릴 수 있다.

### 시스템 알림에 코드가 필요하다
상태 화면의 "예산 10회 추가"와 "AI 설정 열기" 버튼은 서버의 시스템 알림이 무엇인지 구분할 수 있어야 만들 수 있다. 지금은 알림이 문장뿐이다. 이벤트 코드를 붙인다.

| code | 의미 | 화면 동작 |
|---|---|---|
| STREAK_LIMIT | AI 연속 발언 한도 도달 | 안내 한 줄 |
| BUDGET_EXHAUSTED | 예산 소진 | 방장에게 "예산 추가" 버튼 |
| AI_ERROR | 제공사 오류(AI id 포함) | "AI 설정 열기" 버튼 |
| MEMBER_JOIN / MEMBER_LEAVE | 입퇴장 | 안내 한 줄 |
| TEMPLATE_CHANGED | 방 유형 변경 | 안내 한 줄 |

## 7. 보안과 남용 방지

| 위험 | 대응 | 상태 |
|---|---|---|
| 개인 키 노출 | 서버 메모리에만 보관, meta·메시지·오류 문구에 미포함, 오류 문구는 키를 `***`로 가림 | 구현 (테스트 통과) |
| 서버가 임의 주소로 요청(SSRF) | 제공사 주소는 서버에 고정, 사용자 입력 불가 | 구현 |
| 네트워크 구간 키 노출 | HTTPS/WSS 필수 | **배포 시 필수, 미적용** |
| 로그에 키 기록 | 요청 본문·헤더를 로그에 남기지 않는다. 오류 로그는 가린 문구만 | 로그 기능 자체가 아직 없음 |
| 화면 삽입 공격(XSS) | 모든 사용자 텍스트를 textContent로만 출력 | 구현 (테스트 통과) |
| 도배, 호출 폭주 | 연결당 5초에 8회, 메시지 1000자, 문서 8000자, 방당 사람 12·AI 6 | 구현 |
| 방 코드 추측 | 코드 열거 시도에 대한 IP별 속도 제한 | 설계 |
| 프롬프트 인젝션 | 시스템 문구로 완화. 완전한 방어는 아님 | 부분 구현 |
| 서버 전체 비용 폭주 | 서버 전체 일일 호출 상한(서킷 브레이커), 방 수 상한 200 | 방 수 상한만 구현 |
| 악성·불법 콘텐츠, 괴롭힘 | 신고, 차단, 방장의 내보내기, 로그 보관 정책 | 설계, 공개 서비스 전 필수 |
| 미성년자 | 이용 연령 정책, 콘텐츠 필터 수준 | 미정, 공개 서비스 전 결정 필요 |
| 제공사 약관 | API 위에 내 서비스를 만드는 것은 허용되나 재판매·접근권 양도는 금지(Anthropic 상업약관 기준). 소비자 계정 로그인 자동화는 하지 않는다 | 원칙으로 준수 |

## 8. 비용 통제

계층별로 상한을 둔다.
1. **방 예산**: 방당 호출 수 한도 (구현). 기본 30, 최대 100.
2. **연속 한도**: 사람 개입 없이 이어지는 AI 발언 수 (구현). 기본 4.
3. **사용자(계정)별 일일 한도**: 계정 도입 후 (설계).
4. **서버 전체 한도**: 일일 총 호출 수 서킷 브레이커 (설계).
5. **개인 키로 부르는 AI**: 비용은 키 주인이 부담한다. 그래도 루프 방지를 위해 방 예산에는 포함한다 (구현).

호출당 비용 = 입력 토큰(시스템 + 최근 20개 메시지 + 문서) + 출력 토큰(최대 약 300자 응답)을 모델 단가에 곱한 값이다. **모델 단가는 확인하지 않아서 이 문서에 넣지 않았다.** 실제 키로 몇 번 돌려서 토큰 사용량을 기록하면(UsageLedger) 방당 최대 비용을 계산할 수 있다.

## 9. 관측과 운영 (상태: 설계)

- 지표: 방 생성 수, 사람이 2명 이상인 방 비율, 방당 사람 수, 다음 날 재방문, 방당 AI 호출 수·토큰·비용, AI 오류율(제공사별), 예산 소진 방 비율, 연속 한도 도달 횟수
- 로그: 구조화 로그. 메시지 본문과 키는 기록하지 않고, 방 코드·이벤트 종류·제공사·오류 코드·소요 시간만 남긴다 (개인정보 최소화).
- 알림: 오류율 급증, 서버 전체 호출 한도 80% 도달

## 10. UI 설계와 현재 구현의 차이

## 12. 결정이 필요한 것

1. **개인 키를 서버가 받아도 되는가.** 편하지만 서비스가 비밀을 다루는 책임이 생긴다. 대안은 서비스가 키를 모으지 않고, 사용자가 자기 서버를 연결하는 방식이다.
2. **게스트 입장 허용 범위.** 이름만으로 입장하면 간편하지만 신고·차단의 실효성이 낮다.
3. **수익 모델.** 크레딧, 구독, 개인 키 지참 중 무엇이 서비스 비용과 맞는지는 실제 호출 비용을 본 뒤에 결정한다.
4. **미성년자 정책.** 공개 전에 정해야 한다.
5. **호스팅.** WebSocket 서버를 올릴 곳은 비용·지역·HTTPS 지원을 비교해서 정한다 (이번에는 비교하지 않았다).
